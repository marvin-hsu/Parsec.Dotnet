# 安全性注意事項

這一頁講的是 Parsec 用戶端能承諾的界限。以下沒有一項是缺陷，那是這個系統本來的形狀；假設不
是這樣的應用程式，才是會受傷的那個。

## 用 Parsec 換到什麼

私鑰那一半從來不會進到你的行程。它在 provider 裡面產生、在 provider 裡面使用，而且除非金鑰
政策另外允許，否則根本無法匯出。你的應用程式發生記憶體洩漏，不會洩漏那把金鑰。

這就是值得擁有的性質，而底下大部分內容講的都是「不要不小心把它送掉」。

## 這條通道兩個方向都沒有驗證

回應沒有簽章。用戶端無法分辨真正的服務與任何在同一個 socket 上回應的東西，而協定也沒有提供
任何可以拿來分辨的機制。

socket 就是信任邊界。任何能寫入它的東西都能扮演服務，而在 Direct 驗證下，任何能寫入它的東西
都能宣稱自己是任何應用程式。把那個 socket 的權限設對不是「強化步驟」，那就是這個部署的安全性
本身。

- 服務支援時優先用 `UnixPeerCredentialsAuthentication`，身分由核心提供，呼叫端無法謊報。
- 用 `DirectAuthentication` 時，把 socket 限制給有資格使用背後那些金鑰的應用程式。名稱是標籤，
  不是憑證。
- 不要把 socket 轉送到網路上。中繼會讓服務看到中繼的憑證，而且會把一條沒有驗證的通道放到別人
  搆得到的地方。

## 受管理行程中的敏感資料

本程式庫交還給你的位元組 —— 匯出的金鑰、共享祕密、明文 —— 都是普通的受管理陣列。這代表：

- 垃圾回收器可能在它們存活期間搬移它們。覆寫你手上那份，碰不到回收器已經在別處做出的副本。
- 作業系統可能把它們換頁到磁碟。
- 它們活到被回收為止，不是活到你不再使用為止。

這在 .NET 程式庫內部無法解決，而用一句方法結尾的 `Clear()` 假裝解決了，比誠實說出來更糟：那
會被讀成一個它給不出的保證。清掉你手上那份仍然值得做 —— 它縮短了暴露窗口，而且不花什麼成本
—— 但要把它當成降低暴露，而不是消除暴露。

真正的答案是根本不要拿到那些材料。在服務裡面簽章，而不是把金鑰匯出來在自己這邊簽；除非真的
有東西需要，否則不要開 `KeyUsages.Export`。

## 金鑰政策是強制執行點

一把金鑰綁定一個演算法與一組權限，服務對每個請求都做檢查。簽章金鑰不會被拐去解密，沒有
`KeyUsages.Export` 的金鑰不會出來。

只授予應用程式真的會用到的權限。`KeyAttributes` 上的工廠方法預設選窄的那邊 —— 除非你傳
`exportable: true`，否則匯出是關的 —— 因為之後放寬是有人刻意做的決定，而事後收緊則意味著要把
金鑰重建一次。

> [!NOTE]
> Mbed Crypto provider 會自己稍微放寬政策：要求 `KeyUsages.SignHash` 的金鑰拿回來時會同時帶著
> `KeyUsages.SignMessage`，因為能對雜湊簽章的金鑰也能對它自己雜湊過的訊息簽章。需要確切知道
> 一把金鑰允許什麼時，把政策讀回來。

## 名稱不是機密，也不是隱私

金鑰名稱是 per-application 命名空間裡的一個 UTF-8 字串。別的應用程式讀不到你的金鑰，但名稱
本身沒有受到保護：不要把祕密編進名稱裡，也不要依賴名稱猜不到。

## 亂數來自 provider

`GenerateRandomAsync` 問的是 provider，在硬體上就是硬體裡的產生器。這是要用它而不是用平台的
原因。用戶端會檢查拿回來的位元組數是不是它要求的數量 —— 一個沒被注意到的短回應，會變成一個
位元數比呼叫端以為的還少的祕密。

## 不該盲目重試的失敗

`ParsecTransportException` 值得重試。`ParsecServiceException` 通常不值得：拒絕是一個決定，而
重複送一個 provider 已經拒絕的請求，通常只會製造負載。特別是不要用迴圈重試驗證失敗 —— 有些
部署會計次。

## 回報問題

本程式庫的安全性問題請走
[SECURITY.md](https://github.com/marvin-hsu/Parsec.Dotnet/blob/main/SECURITY.md) 的流程，不要
開公開 issue。Parsec 服務本身的問題屬於上游，請找 [Parsec 專案](https://parsec.community/)。
